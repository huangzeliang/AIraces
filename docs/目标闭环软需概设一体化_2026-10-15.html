2角色与权限设计

本章回答"谁能看到哪些菜单、能做哪些操作、能看多大范围的数据"，并给出角色配置的数据结构与操作流程。全站权限模型 = 角色（Role）× 权限点（Permission）× 数据范围（Scope） 三元组。

2.1角色定义与职责边界

系统内置三个角色。一句话概括：超管配规则、管理者定方向、员工定细节；对应权限基线 —— "可提不可定"。

超级管理员

super_admin · 系统级 · 数据范围 ALL
  • 配组织：维护部门 / 团队 / 小组层级，定义数据范围边界
  • 配角色：新建 / 复制 / 停用角色，勾选权限点，绑定用户
  • 配字典：岗位与能力标签、变更原因分类、通知渠道、预警阈值
  • 配周期：季度 / 月度周期定义与切换
  • 管数据：导入导出、异常补录修正、审计日志
关注规则一致 · 权限合规 · 数据完整
核心动作配置 / 授权 / 审计
不参与拆解、派工、验收等业务动作

管理者

manager · 部门主管 / 总牵头人 · 数据范围 DEPT
  • 定目标：录入部门重点工作，锚定目标来源与优先级
  • 拆目标：逐级下拆（AI 只出草案）、SMART 质检、权重与时限
  • 派任务：智能派工、饱和度校验、检核确认后下达
  • 盯过程：跟踪进度、审批变更、主动干预与过程指导
  • 做验收：对照标准评分、组织验收、横向对比与归档
关注全局健康度 · 风险预警 · 达成率
核心动作录入 / 拆解 / 指派 / 审批 / 评分
不可做改角色权限、动字典与周期（须超管）

员工

staff · 执行人 · 数据范围 SELF
  • 认目标：查看承接来的目标（含"为什么做"的上游链）与验收口径
  • 拆任务：把承接的任务继续下拆为子任务（员工主导）
  • 自建任务：先自行创建任务进个人清单；挂到目标 / KR 须上级确认
  • 报过程：更新进度、上传证据、记日志、发起变更申请
  • 拿指导：接收预警与 AI 过程指导、查看上级点评
  • 做自评：对照标准自评、提交证据、复盘沉淀
关注我的目标 · 今日待办 · 预警与反馈
核心动作承接 / 更新 / 变更 / 自评
不可做发布目标、审批变更、评分验收

服务端强制原则：① 所有写接口在 app.py 前置钩子做「权限点校验 → 数据范围校验 → 字段白名单校验」三道闸，任一不过返回 1008 权限不足；② 前端隐藏按钮只是体验优化，不等于授权；③ 越权的 objective_id / org_unit_id 参数一律按 1003 资源不存在 处理，不泄露"存在但无权限"的信息。

4.4.1 正向拆解流程（部门重点工作 → 个人每日任务）

拆解链部门目标→ AI 草案 →SMART 校验→拆解树与发布→ 发布 →智能派工→ 下达 →日计划与任务→ 按天分解 →进度更新
  • AI 只出草案：F-103 产出的子目标 / 任务一律落 draft，不进目标树正式结构，必须人工采纳。这是"AI 辅助而非替代"的硬约束。
  • SMART 强校验：五维分开打分（S/M/A/R/T 各 0~20，合计 100），任一维 < 12 分则不允许提交确认；修改建议可一键采纳（F-109）。
  • 发布即快照：发布瞬间把 success_criteria 与 KR 基线写进 published_snapshot —— 后续验收一律对照快照而非当前值，防止"边做边改标准"。
  • 派工前置校验：任何下达动作都要先过 4.4.3 的饱和度校验。
  • 下拆不跨层：管理者下拆到"任务"为止；任务再往下拆子任务由员工主导（F-104 任务层），且子任务不得反向修改目标的成功标准。

4.4.2 反向验证流程（成果 → 上级目标）

验证链完成提报→ 交付物 →AI 证据预审→ 缺失/不一致清单 →完成与验收对照快照评分 →验证证据链→复盘→结果归档→ 上溯校验上级目标
  • 三层结果验证：① 规则验证（F-302 按 calc_strategy 自动算达标 / 未达标 / 数据不足）→ ② AI 证据预审（F-311 指出缺失证据 / 不一致 / 待核实，仅建议）→ ③ 管理者验收（F-303 通过 / 驳回整改）。
  • 逆向指标不算除法：calc_strategy=reverse（如"缺陷数越低越好"）不用 实际 ÷ 目标，改用 2 − 实际 ÷ 目标（封顶 100、下限 0），避免得出反直觉结论（F-312）。
  • 三率分开：任务完成率 ≠ 目标过程完成率 ≠ 目标达成率，驾驶舱分开展示，禁止用任务完成率冒充达成率（F-404）。
  • 证据链可回放：从一条评估结论可一路点开它引用的进度记录 / 证据 / 变更记录（F-307），支撑"可追溯"评分点。

4.4.3 派工饱和度校验与拦截流程（硬约束 ⑥）

派工链选定执行人→试算派工→饱和度实时校验(F-124)→≤ 阈值：放行／> 阈值：拦截 + 三档建议→检核确认后下达(F-121)
饱和度 saturation = current_load_hours / base_capacity_hours × 100% current_load_hours = Σ(该员工所有 status ∈ {todo, doing, blocked} 的 work_task.plan_hours) base_capacity_hours = staff_profile.base_capacity_hours（按周期折算，如季度 480h） 判定（阈值 saturation_limit 默认 90%，由 setting 配置）： saturation ≤ 90% → 放行（绿色） 90% < saturation ≤ 110% → 提示（黄色）：建议关注，可强制下发 saturation > 110% → 拦截（红色）：默认禁止下达，须三选一
  • 三档调平建议（拦截时系统给出，管理者也可自行处理）：① 换人 —— 推荐同能力标签下饱和度最低的 2 人；② 拆期 —— 把任务起止时间拉长到饱和度可承受的区间；③ 减量 —— 拆分任务，只先下发达标所需的关键部分。
  • 豁免与留痕：具备 can_override_load 的管理者（超管可配）可填理由强制下发；强制下发必写审计日志并在任务卡上挂"超载下发"标记，供验收与复盘回看。
  • 关联度与不确定性：除饱和度外，F-118 算"本任务与员工既有个人任务的关联度"，F-119 综合输出"任务量偏大 / 不确定性偏高 / 分配不均"三类风险标 —— 三条都是建议，不是拦截条件；唯一的硬拦截只有饱和度。

4.4.4 日进度上卷公式（本次补充 · 消解冲突 ③）

员工每天拉的是日计划项的进度条，它必须经过两级上卷才能影响目标 —— 中间不能跳步，否则会污染达成率。

第 1 级 · 日计划项 → 任务执行度（只统计 day_status = approved 的日计划项） task.exec_rate = Σ(item.progress × item.plan_hours) / Σ(item.plan_hours) 其中 item.progress ∈ [0,100]，item.plan_hours > 0 第 2 级 · 任务执行度 → 目标过程完成率（只统计挂在目标下的任务） objective.process_rate = Σ(task.exec_rate × task.weight) / Σ(task.weight) 其中 task.weight 取 task_assignee.weight × objective.weight 的归一化值 第 3 级 · 目标达成率（不由日进度上卷，由 KR 按指标口径计算） forward 指标（越高越好）：attainment = 当前值 / 目标值 × 100% reverse 指标（越低越好）：attainment = 2 − 当前值 / 目标值，结果 ∈ [0,100] milestone 指标（里程碑式）：attainment = 已达成里程碑数 / 里程碑总数 × 100% qualitative指标（定性） ：attainment = 评分档位映射值（见 setting.grade_map） 硬约束： · F-412（拉条）只写 daily_plan_item.progress，禁止直接写 objective.progress · work_task.progress = task.exec_rate（自动上卷，来源标 source=daily） · objective.progress 记录的是 process_rate（过程视图）， 与 objective.attainment（达成度）两个字段分开存、分开展示 · 手动更新（F-201）写 progress_log(source=manual)，优先级高于日进度上卷： 若某任务已由管理者手动更新，则该任务的 exec_rate 取手动值（含 manual_override = true）
为什么必须分开：如果员工"每天拉条"就直接改目标完成度，会出现两个后果 —— ① 员工可以把目标完成度"拉"到 100% 而 KR 实际未达成，达成率失真；② 周期末的验收失去客观基准。所以：日进度管"过程节奏"，KR 管"结果达成"，两者分开存储、分开展示、只在复盘时对照。

4.4.5 关键路径与唯一热点阻塞

输入：work_task 集合 + dependency 边集合（FS 关系，lag_days 可负） 第 1 步 · 环检测（F-219） 对依赖图做拓扑排序；若存在环 → 阻断保存并高亮成环链路（返回 1005 + 环上 task_id 列表） 第 2 步 · 关键路径（F-216） 按最早开始 / 最晚开始（ES/LS）计算各任务总时差 total_float total_float = 0 的任务串成关键路径（可能多条） 若关键路径上存在唯一 total_float = 0 且工期占比最高的节点 → 标记为 「唯一热点阻塞」（本次需求要的那个"一延期全延期"的单点） 第 3 步 · 影响传导（F-217） impact_days(task) = max over 关键路径上 task 之后的所有路径的累计工期 输出："该环节延期 N 天 → 项目整体延期 M 天"，并沿传递闭包高亮受影响的后续任务 第 4 步 · 预警联动（F-218） 关键路径高亮与三色预警口径一致：关键路径上任务若为黄/红，则整体项目健康度直接 降一级（因为它是单点）；非关键路径任务的滞后只在局部提示

6.1.5 命名与格式规范（新增接口须遵守）

  • URL：/api/<模块>/<动作>；模块 ∈ auth · role · org · objective · staff · assign · task · today · dep · change · review · retro · compare · workbench · dashboard · settings · data；动作用动词短语（save / publish / commit / submit / approve / progress / generate / import / export）。
  • 分页：入参 page（从 1 起，默认 1）+ page_size（默认 20）；响应统一返回 PageInfo。
  • 排序：入参 sort_by（字段键）+ sort_dir（asc / desc，默认 asc）；未传时取各页默认（任务列表默认 plan_end asc）。
  • 时间：datetime 一律 ISO8601（YYYY-MM-DDTHH:mm:ss），date 用 YYYY-MM-DD；前端展示为 YYYY-MM-DD HH:mm。时间基准一律取服务端 ts，前端不得用本地时间做判定。
  • 布尔 / 空值：布尔用 true / false（禁 1 / 0）；无值统一 null（禁空字符串占位）。
  • 字段名：一律 snake_case 且命中 1.3 数据字典；越界字段先入字典与 1.6 契约再实现。
  • 鉴权：除 /api/auth/login 外，所有接口经 app.py 前置钩子做「权限点 → 数据范围 → 字段白名单」三道校验，任一不过返回 1008。
  • 动作复用：同一资源的多个状态迁移尽量合并在一个 POST 接口里，用 action 入参区分（如 objective/publish 的 action ∈ submit|publish），减少接口数量。

7测试与验收

本章回答"这份文档怎么被验证"。核心取向：确定性规则交给脚本判定，AI 只当"眼睛" —— 算术、枚举、跨页比对写死在代码里，模型只负责"把页面读成结构化数据"。

7.1测试策略

支柱做法为什么这样做
① 测试与开发并行六条业务线各带自己的用例；接口契约（第 6 章）冻结后即可并行写用例，不等前端完成2~3h 冲刺窗口内唯一可行的节奏
② 两轮 AI 分层验证一轮接口与数据层（直接用 curl / 脚本打接口，验字段与错误码）；二轮完整业务流程（浏览器走通"录入 → 拆解 → 质检 → 发布 → 日计划 → 拉条 → 验收"）先保数据对，再保流程通；避免流程看起来能跑但数据是错的
③ AI 自动化 + 人工互补眼睛 = MidScene.js（自然语言操作页面、读成结构化 JSON、逐用例录屏）；裁判 = Python 脚本（算术 / 枚举 / 跨页比对，输出 PASS / FAIL / SKIP）模型只回答"值是多少"，对错由脚本算
④ 缺陷认领闭环缺陷编号 → 关联用例 → 归属模块 → 操作录屏；每次修复都要回归关联用例答辩可当场回放缺陷录屏，物证可查
⑤ 权限用例专项每个写接口都补"越权调用"负向用例（换角色 / 换 objective_id / 绕过前端直调）权限是本项目的设计重点，必须可验证

创新点独到解法为什么有价值落点
① 派工前负荷风险预判 不等事后考核，在派工那一刻先用"饱和度 + 关联度 + 不确定性"三项算出风险，超载直接硬拦截并给三档调平建议（换人 / 拆期 / 减量） 任务量分配不均、个体不确定性高 —— 这些风险其实在派工时就已经埋下，事后发现已经晚了。这是把"管理动作"前移到决策点 F-117~119 · F-124 · 4.4.3
② 唯一热点阻塞与延期传导 从依赖图算关键路径，识别唯一单点瓶颈，并量化"这里延期 N 天 → 整体延期 M 天"；多条关键路径时如实说"无唯一单点"而不强行指认 整体工时里往往只有一个环节真正卡住全局，但没人说得清是哪一个。量化传导链把一个"感觉"变成可决策的数字 F-216~219 · 4.4.5
③ 日粒度过程节奏 + 连续异常双角色提醒 员工把任务按天拆解并走一次轻量审核，之后每天拉一次进度条；连续 3 天未达 100% 时给员工与领导各推一条文案、语气、下一动作完全不同的提醒 把"过程管理"从周期末的滞后指标，变成日频的领先指标；同一条数据对不同角色说不同的话，避免过程提醒变成考核施压 F-409~413 · 2.7.4
④ 变更原因结构化归因 发起变更必须选原因分类（不可留空），沉淀为可统计的组织知识；频繁变更的目标自动预警 直接解赛题原话"计划变更频繁但原因不清"；半年后回看，能回答"我们为什么老在改计划" F-211 · F-214 · api-37
⑤ 发布快照 + 三率分离 发布瞬间固化成功标准与 KR 基线为不可变快照，验收一律对照快照；同时把"任务完成率 / 目标过程完成率 / 目标达成率"三个口径分开存储与展示 防止"边做边改标准"，也防止用任务完成率冒充达成率（"这事做了 100% 条，但目标只达成 40%"是常见的管理失真） F-312 · AC-20/21 · W3
⑥ 角色权限做成真配置 内置三角色 + 可复制自定义角色；权限点分 menu / action / field 三类；数据范围 ALL / DEPT / SELF；内置角色保护 + "至少保留一个超管"的安全兜底 很多作品的角色只是"界面上切一下"；这里把权限做成服务端强制的三道闸，并支持真实组织里的多角色与矩阵式授权 第 2 章 · api-05~07
